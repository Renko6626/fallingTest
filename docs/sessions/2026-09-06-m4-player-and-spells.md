## 1. 这次做了什么

先读文档（项目侧四篇真源 + Noita 社区侧新抓的 30 篇组件文档与玩法页）→ brainstorm 七问裁决
→ spec → 七份分册计划 → 逐 Task 实施 + 评审 + 修复轮 → 整分支评审 + 修复轮。

**范围经用户裁决收窄**：M4 = 会动的生物 + 会飞的投射物。Noita 式施法状态机（牌堆抽取 /
多重 / trigger / timer / shuffle / 法杖构筑）与 stain 状态效果整块顺延。

落地：`InputFrame`（唯一入核通道）+ BAM 角 1024 项查表；生物（自研定点 AABB 逐轴扫掠、
跨台阶、踩得住 M3 刚体盖章格、排开液体、游泳、材质接触伤害、HP 墓碑）；弹体（独立 SoA，
复用 `dda`/`fixed` 模块而非粒子池，含侵彻/弹跳/阻力/穿透/排开/刚体点冲量/定时爆）；
法术表扁平三原语 Bolt/Blast/Spray + cooldown·mana 双闸门。管线第 2 步由占位变生效并展开
2a–2d（协议版本变更），`state_hash` 由 `combine3` 变 `combine4`。

## 2. Noita 侧本轮新查到的（喂进了 spec）

- **施法 = 牌堆状态机**：非 shuffle 就是从左到右的指针；shuffle 只在四个时点洗牌，不是每次
  抽牌随机。modifier/multicast/trigger 是同一机制的三种参数——"抽走后面 N 张一起放"，不够就
  wrap 回头。指针 + 洗牌种子进状态即可 lockstep。**本轮整块推后**。
- **法术 = 扁平数据表，没有脚本**：`ConfigGunActionInfo` ~70 字段全是加数/乘数。这直接回答了
  总纲那条待决——Noita 走到成品也没上 VM。
- **玩家控制器数值可直接抄**：`pixel_gravity=600` / `run_velocity=40` / `jump_velocity_y=-175` /
  `climb_over_y=3` / `liquid_velocity_coeff=9` / swim 三档系数。
- **伤害写受害者侧**：`materials_that_damage` + `material_damage_min_cell_count=4`。
- **弹体 ~80 字段逐条过筛**，收 7 条（排开/定时爆/空气阻力/液体阻力/穿透掩码/刚体冲量/弹跳），
  明确不做 20 余条。侵彻确认为"能量射线三兄弟"的第四个同构用例。

## 3. 四条实测教训（已入总纲 §11 第 18 条 ⑥）

这四条都是**设计文本想当然、被实现或评审证伪**的，是本轮最有长期价值的产出：

1. **扫掠步数不能取速度整数部分**。走速 0.67、重力 0.25 都 < 1 格/tick ⇒ 步数恒 0 ⇒ 碰撞
   检测彻底失效、亚格位移逐 tick 累加直接穿墙。须取"起点格 → 终点格"的格差。（我计划里的
   伪代码就是错的，实施者实测证伪。）
2. **`on_ground` 必须是对当前 footprint 的查询**，不能是扫掠的副作用。第一版修成"未跨格就
   继承上一 tick"，结果水平走出台沿时继承了针对旧位置的 `true`，开出空中跳——两个方向只有
   查询式能同时关上。配套代价：起跳闸门是电平触发，须在两次扫掠之后显式收口。
3. **Noita 三档游泳浮力系数不能直接抄**。它的玩家在水里另有一份独立喷射推力做上升，系数只
   调**被动**浮力；照抄的结果是"按住上"比"什么都不按"沉得更快。（这是我 spec 的缺陷。）
4. **弹体侵彻 = 能量射线三兄弟的第四个同构用例**。删格逻辑从 `explode::fire_ray` 抽出
   `destroy_cell` 两处共享，不新写一套。

另记一条指纹纪律的实测后果：握手指纹是**裸字节哈希**（总纲第 4 条刻意选的，为完备性），
所以 `data/*.ron` 的**纯注释改动**也会移动指纹。这是设计意图不是缺陷，但意味着 golden 重录
的口径必须固定成"只允许指纹行变、仿真哈希行逐位不变"。

## 4. 评审抓到的、值得记住的失效模式

- **测试通过 ≠ 特性存在**：`pass_through` 那条测试用的 `digger` 自带 `dig_power=90`，就算穿透
  分支被删，侵彻照样挖穿 5 格水、断言照样为真。改用 `dig_power=0` 的 `wet_bolt` + 水量不变
  断言才有区分力。
- **golden 与 SyncTest 钉的是确定性、不是内容**：把 `duel.ron` 的输入时间线整段删掉，两者
  照样绿（重录一次即可）。故补 `duel_acceptance.rs` 把"五项行为真的发生"变成断言。
- **终局断言无法归因**：只断言"1 号死了"，一次改坏燃烧参数把它提前烧死也能过，而对射那条
  因果链完全没被验证。补 tick 1700 的中途检查点才逼出归因。
- **`unreachable!()` 挂在 `pub` API 的误用路径上**，且它在 release 下同样触发。不变量要守在
  入口，不是在远端防御。

## 6. 已知限制与遗留

- **水流推人做不了**：网格只有无符号竖直速度位、无水平速度场（`tuning-knobs.md` §6 缺口 #2）。
  M4 的水只做阻力 + 浮力。
- **弹体对刚体的点冲量未按质量/半径归一**，仅在 12×12 尺寸上实测稳定（总纲第 18 条 ⑧ 已披露）。
- **`duel` 的油火连锁点火走 script `Brush(fire)`**，不是法术驱动；法术驱动的完整链路由
  `oil_spray_then_bolt_ignites_a_chain` 覆盖。
- **`CreatureTable::get` 对越界 template 裸索引 panic**，M5 一旦 Op 来自线上就是远程 panic 面
  ——**M5 动工前必须关**。
- **GIF 目检未做**（spec §0.2 验收第 6 项），待用户。
- 其余延期项见最终评审的 13 条分类表（`.superpowers/sdd/` 内报告，随工作区清理消失，
  故要点已并入本节与总纲第 18 条 ⑧）。

## 7. 过程侧的教训

- **三个 agent 卡在"挂后台等命令、停下等通知"上**，各白烧一轮；第三次在 dispatch 里写死
  "所有命令前台跑完"仍然发生。这类 agent 在长命令上有稳定的行为倾向，后续派发要把长命令
  拆成必须逐条前台执行的步骤。
- **全量套件 ~7 分钟**（含 2 万 tick × 六配置 SyncTest），每个 Task + 每个修复轮各跑一次，
  是本轮 11 小时墙钟里的大头。后续可考虑给 SyncTest 分层（PR 级跑短的、合并前跑全的）。
- **Task 7 与最终修复轮的实施者都在收尾前掉线**，由控制器接手——这两处是**实施与验证同一方**，
  最终评审已就 Task 7 加倍审过并查出一条真漏（⑤ 的因果归属）。
